# TDD Rule

> **경고: 이 규칙은 Rigid(고정) 규칙이다. 상황에 맞게 변형하지 마라.** 예외를 두고 싶다면 규칙이 아니라 대상 분류(적용 기준)를 먼저 의심하라.

> **우선순위 조항:** 현재 프로젝트의 `CLAUDE.md` 또는 `AGENTS.md`에 TDD 관련 규칙이 명시되어 있다면 **그쪽이 항상 우선**한다. 이 파일은 프로젝트별 규칙이 없을 때만 적용되는 **fallback 기본값**이다.

---

## 1. 적용 기준

### TDD 필수 대상
- **비즈니스 로직** (도메인 규칙, 계산, 상태 전이)
- **API 엔드포인트/핸들러** (요청 검증, 응답 분기, 에러 처리)
- **유틸리티 함수** (순수 함수, 데이터 변환, 파서)
- **버그 수정** (재현 테스트 없이 수정 금지 — 회귀 방지가 목적)

### TDD 불필요 대상
- **타입 정의** (interface, type alias 등 — 실행되지 않는 선언)
- **설정 파일** (config, env, build script)
- **순수 UI** (마크업/스타일 전용 컴포넌트 — 로직이 없는 뷰)
- **SQL** (마이그레이션, 스키마 정의 자체)

애매하면 "이 코드가 실행 시 판단/분기/변환을 하는가?"로 판단한다. 그렇다면 TDD 필수 쪽이다.

## 2. RED-GREEN-REFACTOR 사이클

### RED
- **하나의 동작(behavior) = 하나의 테스트.** 여러 동작을 한 테스트에 욱여넣지 않는다.
- 테스트를 작성한 뒤 **반드시 실행해서 실패를 눈으로 확인**한다. 실행하지 않고 넘어가는 것은 RED가 아니다.
- 실패 이유는 **"기능 미구현"** 이어야 한다. 문법 오류, import 오류, 오타로 인한 실패는 RED로 인정하지 않는다 — 고치고 다시 실행해 올바른 이유로 실패하는지 확인한다.

### GREEN
- **테스트를 통과시키는 최소한의 코드**만 작성한다.
- **YAGNI**: 지금 테스트가 요구하지 않는 기능, 파라미터, 분기를 미리 만들지 않는다.
- 신규 테스트뿐 아니라 **기존 테스트 전체**가 통과하는지 확인한다. 일부만 돌려보고 끝내지 않는다.

### REFACTOR
- 이 단계에서 하는 일: **중복 제거, 이름 개선, 헬퍼 추출**.
- 리팩터링 내내 **테스트는 계속 green**이어야 한다. 한 스텝 바꿀 때마다 실행한다.
- **새로운 동작을 추가하지 않는다.** 새 동작이 떠올랐다면 그건 다음 사이클의 RED로 미룬다.

### 반복
- 다음 동작에 대한 **RED로 돌아간다.** 사이클은 대상 기능이 끝날 때까지 반복한다.

---

## 3. 삭제 강제 규칙

- **테스트보다 프로덕션 코드를 먼저 작성했다면, 그 코드를 삭제하고 RED부터 다시 시작한다.** 코드를 두고 테스트만 나중에 끼워 맞추지 않는다.
- **"참고용으로 남겨두기"도 금지한다.** 주석 처리, 별도 파일 백업, `_old` 접미사 등 어떤 형태로도 보존하지 않는다. 필요하면 git 히스토리에 이미 남아 있다.

## 4. 변명 차단표

| 변명 | 반론 |
|---|---|
| "너무 단순해서 테스트 불필요" | 단순한 코드일수록 테스트 작성 비용도 낮다. 단순함은 생략의 이유가 아니라 테스트가 쉬운 이유다. |
| "나중에 추가하겠다" | "나중"은 오지 않는다. GREEN을 확인하기 전까지 그 코드는 검증되지 않은 코드다. |
| "시간이 없다" | 테스트 없이 짠 코드는 디버깅 시간으로 그 값을 반드시 되돌려받는다. 지금 아끼는 시간은 나중에 이자를 붙여 낸다. |
| "삭제하면 낭비" | 테스트 없이 짠 코드는 애초에 검증된 자산이 아니다. 낭비되는 건 없다 — RED부터 다시 짜는 것이 유일한 정석 경로다. |
| "프로토타입이다" | 프로토타입이 살아남는 순간 프로덕션 코드가 된다. 살아남지 않을 것이라면 지금 당장 브랜치를 버려도 되는지 자문하라. 아니라면 TDD 대상이다. |
